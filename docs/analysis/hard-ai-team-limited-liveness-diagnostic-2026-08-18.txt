Hard AI liveness under team-limited information — diagnostic report
====================================================================

-------------

Executive diagnosis
-------------------
The dominant failure is not that Hard fails to attack before scouting. It does
reach minArmyToAttack = 5 from friendly state alone and issues attack commands
before meaningful contact.

The failure is that, once information is unknown or memory expires, Hard's
buildArmy goal contains no positive combat-development value:

  buildArmy: {
    recoveryProgress: 0,
    combatEfficiency: 0,
    counterValue: 1.00,
    buildCycleBias: 0.25,
  }

With no fresh enemy composition:

  * counterKind is null;
  * counterValue is zero for every candidate;
  * the only remaining preference is the build-cycle slot;
  * miner slots therefore still select miners while the army is below the
    attack threshold or rebuilding.

The old omniscient version had enemy composition continuously from match start.
That repeatedly supplied counterKind, giving a combat unit counterValue = 1.0
and overriding miner-oriented portions of the cycle. It therefore assembled
materially larger combat forces before the first serious engagement.

Under limited vision, Hard attacks with a thin five-unit force, loses enough
units to fall below five, transitions back to buildArmy/defend, then rebuilds
using the ordinary miner-containing cycle rather than a combat-readiness
priority. This repeats. The economic queue remains active, but it converts
heavily into protected miners and only intermittently into a sustainable
fighting force.

Decision-chain audit
--------------------
Current flow is as intended architecturally:

  authoritative world
  -> simulation-owned current team vision
  -> copied visible observation + bounded team memory
  -> assessment
  -> strategic goal
  -> turret side path / feasibility
  -> unit utility
  -> committed production
  -> command

Information boundary

  * updateAiMemory() consumes getVisibleEnemyEntities() only.
  * Current visible and remembered mobile composition feed estimated enemy
    power.
  * Mobile memory lasts six seconds for Hard.
  * Near-home threat uses current visible enemies only.
  * No hidden entity references, HP/state tracking, or global composition route
    remains.

Friendly-state signals already available

Assessment already has all information needed for baseline readiness:

  * living miners, warriors, archers, and heroes;
  * combatUnits;
  * friendlyPower;
  * gold, queue, population/cap;
  * recovery state;
  * current command;
  * minArmyToAttack;
  * selected strategic goal.

The strategic goal already recognizes the friendly-state threshold:

  * fewer than 5 combat -> buildArmy;
  * 5 or more combat, absent live threat or relative underpower -> attack;
  * an attacked force reduced to zero -> recover.

The disconnect is downstream: buildArmy identifies the need correctly but gives
utility no reason to fulfill it preferentially.

Command behavior

pickCommand() is not blocking pre-contact offense:

  return combatUnits >= difficulty.minArmyToAttack ? 'attack' : 'defend';

It uses friendly combat count. It does not require enemy sighting, enemy power,
or a counter pick to attack.

Unknown versus zero semantics
-----------------------------
There is no hidden-world leak, but there is an important semantic collapse at
the strategy boundary.

Correct distinctions already present:

  * lastScoutedAt === null distinguishes never-observed from recently-observed.
  * isMemoryFresh() returns false when no observation exists.
  * enemyNearHome correctly requires current visible contact.
  * underpowered requires estimatedEnemyPower > 0, so unknown enemy power does
    not incorrectly trigger a relative-power retreat.

Where unknown and zero converge materially:

  * empty or unknown composition produces estimated power 0;
  * counterPick() gives null for no composition, empty composition, and balanced
    composition;
  * null counter gives no counterValue;
  * under buildArmy, with combat terms set to zero, the build cycle becomes the
    only live purchase preference.

This is not a bug that falsely claims “enemy power equals zero, therefore
attack.” Hard already attacks from its own threshold. It is a missing policy
semantic: “enemy information is unavailable, therefore continue building a
viable own army.”

Pre-contact strategy assessment
-------------------------------
Before reliable enemy contact, Hard currently:

  1. enters buildArmy below five combat units;
  2. buys combat only when the current build-cycle slot is combat;
  3. buys miners at miner cycle slots because no counter signal outranks them;
  4. reaches five combat units in most seed/team cases;
  5. attacks without needing scouting;
  6. loses enough units to fall below threshold;
  7. returns to buildArmy, where the same cycle behavior resumes.

The build cycle can eventually assemble a threshold-sized army, but it does not
maintain enough combat pressure to survive the repeated threshold-loss loop.
Miner production is not an absolute production lockout; it is strategically
inappropriate while buildArmy is active because the utility model has no
friendly-state military deficit term.

Enemy-dependent vs. baseline behavior
--------------------------------------
Legitimately enemy-dependent:

  * counter-unit selection;
  * estimated enemy power and relative-underpower retreat;
  * confirmed near-home defense;
  * hero counter choice;
  * tactical response to visible composition.

Should not require enemy information:

  * recovering from zero combat;
  * growing from fewer than minArmyToAttack to a viable army;
  * maintaining baseline combat readiness after losses;
  * deciding the army is too thin for sustainable ordinary pressure;
  * producing a default fighting force before or between sightings.

Smallest recommended change
---------------------------
Do not change vision, memory, scouting, counters, attack threshold, economy,
balance, or build cycle.

In a separately approved strategy scope, add one reusable friendly
combat-readiness / combat-deficit signal to the existing Hard utility path,
active when the current goal is buildArmy (and likely shared with recover).

The smallest implementation form is likely to make buildArmy positively value
combat candidates through the existing utility dimensions, especially the
existing recoveryProgress and combatEfficiency, instead of adding a special-case
“blind attack” rule.

Conceptually:

  if own combat units < minArmyToAttack:
      prefer an affordable combat unit over a miner
  else:
      retain current counter/build-cycle behavior

Why this is the smallest clean fix:

  * It uses only authoritative friendly state already present in assessment.
  * The existing goal selection already encodes the deficit boundary.
  * It does not need to infer hidden enemy strength.
  * It preserves counter behavior once enemy composition is actually known.
  * It corrects the exact point where buildArmy currently becomes cycle-only.
  * It addresses both first assembly and post-combat rebuilding.

The production value should be named combat-readiness progress, not recovery,
because buildArmy includes normal pre-contact development as well as literal
recovery.

Secondary recommendation
------------------------
After validating the narrow buildArmy readiness change, inspect whether Hard
needs a second, small standing-force maintenance condition while nominally in
attack.

Once it reaches five and switches to attack, current unknown-information
purchase selection again becomes primarily build-cycle-driven. Test the first
change alone first; it may be sufficient because combat losses naturally return
Hard to buildArmy. Do not preemptively add the second rule.

Raven implication
-----------------
Raven should improve an already functioning baseline through:

  * earlier and longer composition refresh;
  * better counter selection;
  * better relative-power assessment;
  * better defense response;
  * more informed attack timing.

Raven should not be required for ordinary military development or for Hard to
be capable of attacking. The present implementation does not make scouting a
prerequisite for issuing attacks; it makes scouting disproportionately important
to production quality because the only non-cycle buildArmy utility signal is a
composition-derived counter.

Correct the friendly-state baseline first. Raven can then raise decision quality
rather than act as a mandatory liveness patch.
